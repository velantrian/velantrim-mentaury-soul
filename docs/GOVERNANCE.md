## § 1. Core Authority Principle

```text
SOLO_MAINTAINER MERGE_PERMISSION
≠
DOMAIN RUNTIME_ACTIVATION PERMISSION
```

A single maintainer with merge authority to a branch can legitimately approve documentation changes and infrastructure code. Runtime activation of experimental systems requires separate, independently-derived technical validation — not inferred from merge authority.

## § 3. Independence Semantics

**Definition:** Two complementary types of independence must not be conflated.

### § 3.1 INDEPENDENT_HUMAN_REVIEW

A technical or architectural decision has received scrutiny from a distinct human reviewer with:

- Different background or perspective from the original author
- No shared authority over the decision's domain
- Documented disagreement resolution or explicit agreement record
- Tracked in issue or PR context (e.g., Issue #39 for reviewer identity audits)

**Example:** A solo maintainer writes docs about merge authority; an independent reviewer from operations or security validates the claim from their domain perspective.

**Authority:** Creates credibility for a decision. Does NOT create runtime capability by itself.

### § 3.2 INDEPENDENT_TECHNICAL_VALIDATION

A technical capability or runtime decision has received separately attributable proof:

- Evidence generated by a system or process distinct from the original authority
- Proof artifact traceable to its own source (test suite, external tool, peer implementation)
- Validation gate that can independently reject the claim if evidence fails
- Owned by a specific governance gate (not inferred from documentation approval)

**Example:** A proposal to activate character runtime requires:
1. P0 Event Substrate passes its own evidence gate (independent from this proposal)
2. Character scenario tests pass (independently authored test corpus)
3. Governance review confirms both gates are owned and enforced

**Authority:** Creates capability to proceed. Cannot be waived by documentation approval or reviewer consensus alone.

### § 3.3 AUTOMATED_ASSISTED_REVIEW

LLM or tool-assisted analysis contributes useful feedback but carries lower weight than human review. Tools can:
- Flag structural issues
- Suggest consistency improvements
- Catch syntax or formatting problems

Tools cannot:
- Create independent human judgment
- Serve as independent technical validation without human confirmation

## § 4. Gate Semantics

A "gate" is an explicit, owned checkpoint that must be satisfied before a capability becomes available.

```text
Gate = specific checkpoint
Gate owner = authority responsible for validation
Gate status = one of:
  - OPEN (ready to accept evidence)
  - BLOCKED_PENDING_REQUIRED_VALIDATION (awaiting evidence)
  - SATISFIED (evidence accepted, capability unlocked)
  - REJECTED (evidence failed, capability unavailable)
  - DEFERRED (intentionally postponed)
```

Character runtime activation is currently:

```text
Gate: CHARACTER_RUNTIME_ACTIVATION_GATE
Owner: (to be designated in architecture decision)
Status: BLOCKED_PENDING_REQUIRED_VALIDATION
Requires: Independent technical validation of substrate + Character scenario contracts
```

The block is intentional and durable — not a temporary delay but an architectural requirement.

---

## § 5. Documentation Authority vs. Runtime Authority

```text
Doc approval  → decision is recorded and justified
Reviewer OK   → decision survived scrutiny
Tests pass    → implementation matches spec

Runtime activation → separate, explicit gate satisfied
```

A documented decision with good justification and passing tests is NOT a runtime activation unless that specific gate explicitly permits it.

---

## § 6. Reconciliation

All references to "independently validated" or "independent validation" in research documents shall mean one or both of the independence types defined in § 3, with explicit reference to which gate(s) are being cited.
