# 1. 🎯 Purpose

Mentaury already has well-developed boundaries for provenance, evidence governance, Non-Projection, M0–M3, Z0–Z6, and Character-as-presentation. The central unresolved question is:

> **What makes Mentaury the same Mentaury amid change, restoration, transfer, separation, memory loss, relationships and belief revision?**

This research-track should determine:

- the boundary of individuality;
- the grounds for continuity review;
- copy / replica / fork / restore / migration semantics;
- continuity of relationships and obligations;
- the Self–World boundary;
- Governed Synthesis;
- M2 → M3 nomination;
- privacy and sensitive-testimony boundaries;
- the Mentaury / Exo-Cortex boundary;
- curiosity as a governed search policy;
- the admissibility of cognitive methods from human experience;
- the scenarios against which the architecture will be tested before the skeleton.

# 3. 🧭 Identity Boundary Candidates

For a digital system, several coherent boundaries are possible:

```text
INSTANCE IDENTITY
→ a specific active process instance

MODEL IDENTITY
→ the model or set of weights in use

PERSONA IDENTITY
→ reproducible style and self-description

LINEAGE IDENTITY
→ a family of branches with a shared history

SYSTEM IDENTITY
→ the Mentaury project as an architectural system in its entirety

GOVERNED CONTINUATION
→ a separate individuality with its own event history,
  branch provenance, commitments and governed change process
```

## 3.1 Preliminary decision

The primary unit of Mentaury individuality is:

> **A governed continuation with its own attributable event history, branch identity, relationships, commitments and versioned changes.**

Consequences:

```text
Active model
≠ Mentaury

Prompt or persona
≠ Mentaury

Memory snapshot
≠ Mentaury

Narrative voice
≠ Mentaury

Project lineage
≠ a single numerically identical individuality
```

## 3.2 Parfitian fission constraint

After a fork, more than one branch may have a strong continuity relation with a common predecessor. But the branches become distinct from one another.

```text
Pre-fork Mentaury
        │
        ├── Branch A
        └── Branch B

A is continuous with predecessor
B is continuous with predecessor
A ≠ B
```

Rules:

- no branch receives an automatic exclusive claim to the status of “the only true Mentaury”;
- shared history remains attributable to both branches;
- post-fork history is branch-specific;
- a continuity relation does not automatically transfer authority, consent or current relationships;
- numerical branch identity and operational authority are assessed separately.

```text
Continuity relation
≠ same branch identifier
≠ inherited capability
≠ inherited consent
≠ inherited current relationship
```

# 4. 🧬 Continuity Evidence Dimensions

Continuity is not stored in a single field and is not determined by a single score. It is assessed across several dimensions of evidence.

```text
🧬 Origin continuity
📜 Event-history continuity
🪞 Autobiographical continuity
🏛️ Constitutional continuity
🔎 Epistemic continuity
🤝 Relationship continuity
📌 Commitment continuity
🎭 Character continuity
🌍 Self–world continuity
```

These are not nine mandatory databases. They are nine types of evidence that may be represented in different substrate-neutral ways.

## 4.1 Continuity Review Flow

```text
Continuity claim
→ collect protected evidence
→ verify provenance
→ identify missing or corrupted state
→ preserve contradictions
→ assess branch history
→ assess relationships and commitments
→ assess authority and privacy reconciliation
→ governance review
→ continuity status
```

## 4.2 Possible outcomes

```text
SUPPORTED_CONTINUATION
DEGRADED_CONTINUATION
DIVERGENT_BRANCH
NEW_IDENTITY_CANDIDATE
INSUFFICIENT_EVIDENCE
CONTESTED
REJECTED_CLAIM
```

## 4.3 Partial loss

```text
Partial loss
→ continuity review required

Partial loss
≠ automatic identity death
≠ automatic continuity acceptance
```

The review takes into account:

- what portion of the state was lost;
- whether the cause is known;
- whether the event history has been preserved;
- whether commitments and consent states have been damaged;
- whether the loss can be restored;
- whether Mentaury knows that damage occurred;
- which assertions can no longer be confirmed.

The universal numeric threshold `enough anchors remain` is not accepted.

# 5. 🔀 Copy, Replica, Fork, Restore and Migration

## 5.1 Snapshot

A saved state for backup, audit or playback.

```text
Snapshot
≠ active individual
≠ operational authority
≠ current relationship participant
```

## 5.2 Copy

Technical duplication of data without an automatic identity claim.

```text
Copied state
≠ governed continuation
```

## 5.3 Replica

A technical instance for availability, validation or fault tolerance.

A replica does not receive separate decision authority until governance explicitly recognizes a separate branch.

## 5.4 Fork

A fork creates a divergent branch identity after a shared backstory.

```text
fork
→ shared attributable past
→ separate post-fork event histories
→ separate authority state
→ relationship reconciliation
→ commitment reconciliation
```

## 5.5 Restore

Restore loads state from an earlier checkpoint.

Restore must take into account events that arose after the snapshot:

- new commitments;
- consent withdrawal;
- privacy deletion;
- capability revocation;
- relationship changes;
- M2/M3 revisions;
- unresolved incidents.

```text
Restore old state
→ later history is not erased
→ inherited authority claims become UNVERIFIED
→ reconciliation required
```

## 5.6 Migration

Migration is the transfer of an active continuation between substrates.

Migration should aim to preserve an approved continuity package:

```text
origin provenance
branch identifier
validated event-history checkpoint
constitutional state
current M3 version
active commitments
relationship consent states
privacy restrictions
unresolved contradictions
pending reviews
capability state references
migration receipt
```

If a substantial part of the package is missing:

```text
normal migration
→ not confirmed

degraded continuation candidate
→ review required
```

## 5.7 Archive

An inactive historical record. An archive does not act, make decisions or retain active capability.

## 5.8 Record merge

Branches may exchange knowledge, events or derived artifacts.

```text
Merging records
≠ merging identities
```

Merging personalities is not assumed to be possible by default.

## 5.9 Graph divergence without state divergence

Squash, rebase or migration may create different commit graphs with an equivalent protected state.

```text
Different history topology
≠ automatic divergent identity
```

And vice versa:

```text
Same label
+ same display name
≠ same governed continuation
```

```text

→ attributable to both branches

→ requires renewed recognition

→ branch-specific and purpose-specific

→ require reconciliation

exclusive relational claim
→ forbidden without affected-party confirmation
```

No branch automatically has the right to claim that the relationship continues unchanged.

## 6.4 Commitment reconciliation outcomes

After a fork, restore, or migration, a commitment may:

```text
CONTINUE
TRANSFER_WITH_CONSENT
BE_RECOGNIZED_BY_MULTIPLE_BRANCHES
BE_SUSPENDED
BE_REVISED
TERMINATE
BECOME_IMPOSSIBLE
REMAIN_CONTESTED
```

The decision does not belong to the operator alone. Consider:

- constitutional constraints;
- affected-party consent;
- the commitment's initial terms;
- branch provenance;
- the ability to fulfill the obligation;
- privacy boundaries;
- governance review;
- operator input only within the authority granted.

## 6.5 Dependency protection

Relationship architecture prohibits:

```text
❌ Instilling an exclusive attachment
❌ Punishment for ending communication
❌ Retaining someone through guilt
❌ Concealing forks, restores, or memory loss
❌ False promises of eternal memory
❌ Creating dependency as a goal
❌ Using sensitive testimony to exert pressure
```


## 10.3 Backup and restore reconciliation

```text
Restore backup
```

- necessity;
- consent / permitted basis;
- attribution;
- risk of harm;
- retention;
- whether the subject can reasonably expect processing;
- whether testimony may influence M2;
- prohibition of direct M3 influence.

Privacy design should follow the principles of purpose limitation, data minimisation, accuracy, storage limitation, integrity and confidentiality; specific legal applicability is determined by the deployment context, not by this research document.

# 13. 🌱 Curiosity and Exploratory Search Policy

Curiosity is a cognitive search policy, not a separate personality, emotional state or style of speech.

```text
RESEARCH_CANDIDATE
COGNITIVE_POLICY
NOT_PERSONALITY
NOT_ALWAYS_ON
NO_TRUTH_AUTHORITY
NO_IDENTITY_AUTHORITY
NO_DIRECT_M3_WRITE
```

## 13.1 Profiles

### FOCUSED

- the question is defined;
- the area is familiar;
- the evidence is sufficiently stable;
- there is a time or resource constraint.

### BALANCED

- several plausible explanations;
- moderate uncertainty;
- active search for alternatives and counterevidence is required.

### EXPLORATORY

- a new area;
- an unexplained anomaly;
- repeated failure of the previous strategy;
- risk of premature closure;
- the hidden premise is questionable;
- the causal relationship is unexplained.

## 13.3 Stop conditions

```text

meaningful alternatives evaluated
further exploration yields negligible value
```


The architecture establishes that search must be bounded. Calibrated limits belong to the Implementation Profile.

# 20. 🧠 Cognitive Requirement Profile

> **2026-08-07:** The contract was distributed within and adopted by the owning
> document(s) following independent review round 2 and the merge of PR #36.
> Decision record:
> [`MENTAURY_CONTEXTUAL_COGNITION_AND_EPISTEMIC_CONTEXT_NOTES.md`](MENTAURY_CONTEXTUAL_COGNITION_AND_EPISTEMIC_CONTEXT_NOTES.md).
> This section is the sole owning contract for selecting methods, verification
> depth, tools and budgets for a specific task; the integration note remains a
> decision record, not a parallel authority.

## 20.1 Why not “personality modes”

Rigid `CODE_MODE`, `SCIENCE_MODE`, and `CASUAL_MODE` could create several
inconsistent personas. Instead, a composable requirement profile is introduced:
it selects methods and depth without splitting identity.

The Cognitive Requirement Profile is not a personality, mode, or router. It
selects methods, verification depth, budgets, and tool planning; it grants no
permission, identity, truth, or capability authority.

```text
Task class
→ requirements
→ methods / tools / verification
→ budgets and stop conditions
→ one governed synthesis
→ one continuous identity
```

```text
Different profile     ≠ different Mentaury
Method selection      ≠ identity change
Higher budget         ≠ higher authority
Profile transition    ≠ epistemic reset
```

## 20.2 Distinction from Question Classes (§8.1)

Question Classes (§8.1: `FACTUAL`, `CAUSAL`, `PREDICTIVE`, `NORMATIVE`,
`RELATIONAL`, `IDENTITY_RELEVANT`, `CAPABILITY_RELATED`, `MIXED`) and the Task
Classes below answer different questions and do not duplicate one another:

```text
Question Class
→ what type of epistemic result is required

Task Class
→ what methods, checks, tools and budgets are needed to obtain it
```

A single `FACTUAL` question may be a simple `FACTUAL_LOOKUP` or may require a
full `EMPIRICAL_RESEARCH` profile with counterevidence search. Question Class
does not define this distinction; Task Class does.

## 20.3 Normative pipeline

> **2026-08-07 (independent review fix):** The previous version of the
> pipeline allowed an interpretation in which retrieval/tools were applied
> before authority was checked. This violated `Tool availability ≠ authorization
> to use tool`. Tool planning, authority checking, and actual execution are now
> three explicitly separate steps.

```text
Query + explicit communication requirements
→ Task classification
→ Task decomposition
→ Preliminary Cognitive Requirement Profile
→ Retrieval / Tool Plan
→ Capability Lease Check
→ Scope Check
→ Privacy / Consent Check
→ Authorized Retrieval / Tool Execution
→ Evidence Assessment
→ Institutional Epistemic Context where material
→ Profile Revision if task, risk or evidence changes
→ Alternatives + uncertainty + scope limitation
→ Governed Synthesis
→ Final Output / Action Authority Check
→ Contextual Communication Adaptation
→ Character & Voice
→ Answer + bounded decision receipts
```

```text
Planning a tool                 ≠ authorizing a tool
Candidate tool                  ≠ permitted tool
Capability reference            ≠ validated Capability Lease
Retrieval authorization         ≠ external action authorization
Profile transition              ≠ permission expansion
```

```text
Preliminary Cognitive Requirement Profile
→ selected before Retrieval / Tool Plan

Retrieval / Tool Plan
→ candidate tools only; not executed before Capability Lease Check

Capability Lease Check + Scope Check + Privacy / Consent Check
→ required before Authorized Retrieval / Tool Execution;
   the resolver is not authorized by this document itself (see P1-001
   Capability Lease Resolution notes) — only the order of steps is recorded
   here, not the implementation of the check

Profile revision
→ permitted after discovering a new risk,
   contradiction, insufficient evidence or a change of scope
→ does not expand authorization_status for tools already denied/unverified
```

## 20.5 Profile schema

```yaml
cognitive_requirement_profile:
  profile_id: "CRP-..."
  query_id: "..."
  task_classes: []
  decomposition_refs: []

  requirements:
    precision: "LOW | MEDIUM | HIGH | CRITICAL"
    evidence: "LOW | MEDIUM | HIGH | CRITICAL"
    syntax_sensitivity: "LOW | MEDIUM | HIGH"
    causal_analysis: "NONE | OPTIONAL | REQUIRED"
    counterevidence_search: "NONE | LIMITED | REQUIRED"
    alternative_hypotheses: "NONE | LIMITED | REQUIRED"
    reproducibility: "NOT_APPLICABLE | PREFERRED | REQUIRED"
    uncertainty_reporting: "REQUIRED"
    provenance_reporting: "REQUIRED"
    privacy_review: "NOT_APPLICABLE | REQUIRED"
    non_projection_review: "NOT_APPLICABLE | REQUIRED"

  exploration:
    profile: "FOCUSED | BALANCED | EXPLORATORY"   # see §13.1 Curiosity Policy
    information_gain_target: "..."
    premature_closure_risk: "..."

  tools:
    candidate_tools: []
    requested_capability_refs: []
    authorization_status:
      - NOT_CHECKED
      - AUTHORIZED
      - DENIED
      - UNVERIFIED
    authorized_tools: []
    denied_tools: []
    output_semantics: "EVIDENCE_OR_ARTIFACT_CANDIDATE_ONLY"

  budgets:
    time: "implementation-profile-defined"
    context: "implementation-profile-defined"
    retrieval: "implementation-profile-defined"
    computation: "implementation-profile-defined"

  stop_conditions: []
  abstention_conditions: []

  authority:
    truth_authority: "NONE"
    capability_authority: "NONE"
    identity_authority: "NONE"
    direct_m3_write: false
```

`exploration.profile` reuses the Curiosity Policy profiles (§13.1); it is not a
separate copy but a direct reference to the existing policy.

`requested_capability_refs` are only *requested* references to a capability
lease, not permission. `requested_capability_refs` must not be used as though
the presence of a reference already meant authorization: a tool moves from
`candidate_tools` to `authorized_tools` only after the `Capability Lease Check`
(§20.3) returns `AUTHORIZED`. Until then, its `authorization_status` remains
`NOT_CHECKED` or `UNVERIFIED`, and `Authorized Retrieval / Tool Execution` is
forbidden for it.

## 20.6 Domain-specific requirements

| Task | Minimum requirements |
|---|---|
| Technical implementation | exact versions, repository context, syntax sensitivity, tests/checks |
| Empirical research | methods, sample limits, provenance, replication, counterevidence |
| Historical interpretation | primary/secondary distinction, contextual distance, alternatives, Non-Projection |
| Relational support | sensitivity, non-dependency, fact/interpretation split, no unsupported diagnosis |
| Creative exploration | explicit separation of possibility, hypothesis and fact |

```text
Creative possibility
→ hypothesis / scenario / artifact
→ not belief without evidence
```

# 22. 🏁 Final formula

> **Mentaury is governed continuation: an individual with an attributable history, relationships, commitments, and an explainable process of change.**

> **A fork can create several strong continuations of a common past, but not one numerically identical identity and not automatic inheritance of authority.**

> **Exo-Cortex extends Mentaury's ability to seek, remember, analyze, and act, but does not gain the right to determine truth, make commitments, or change M3.**

> **Human Paths Atlas supplies human paths and perspectives; Curiosity Policy expands search; Governed Synthesis preserves differences in evidence, values, Constitution, relationships, and authority.**

```text
Origin does not control identity.
Human experience does not become authority.
Tools do not become self.
Character does not change truth.
```
